# 번식 제한 서버 ZDO 구현 보관본

2026-10-05 사용자 요청으로 서버 집계 구현을 보관하고 활성 코드를 이전 로컬 인스턴스 캐시 방식으로 되돌렸다. 이 폴더는 현재 빌드·배포 패키지에 포함되지 않는다.

- `snapshot/`: 롤백 직전 관련 소스, 연결 코드, 문서와 테스트 10개 파일의 원본 사본.
- `baseline/`: 이번 롤백 직후의 관련 파일. 다른 작업의 기존 변경을 포함하므로 Git HEAD와 다르다.
- `reapply.patch`: baseline에서 서버 집계 구현으로 돌아가는 변경만 담은 패치. 기존 Orb 및 원본 게임 DLL 접근 대응을 되돌리지 않는다.
- `artifacts/FeedLikeGrandma.Debug.dll`: 롤백 직전 최종 병합 Debug DLL. 서버 집계 외에 당시 작업 중이던 Orb·호환성 패치도 포함한다. 배포용 Release가 아니다.
- `SHA256.json`: 보관 소스와 DLL의 해시. 소스 사본은 저장 직후 원본과 대조했다.

보관 DLL SHA-256: `603BDF4CFB55A9A60F4273484A8DDAC59BF81C5663969F54112B5780304EDC9E`

당시 저장소 HEAD는 `28152bd6763d95bed8e1bea024e3db428a6884f0`, 모드 버전은 작업 트리의 `1.1.3`이었다. 이 보관본을 위해 버전 변경, Release 빌드, ZIP 생성 또는 커밋은 하지 않았다. `snapshot`은 전체 프로젝트 사본이 아니므로 그 안의 프로젝트를 직접 빌드하지 않는다.

## 재적용

저장소 루트에서 아래 명령으로 먼저 현재 소스와의 적용 가능성을 검사한다. 이후 소스가 변경되었다면 충돌 내용을 검토하고 통합하며 snapshot의 연결 파일 전체를 덮어쓰지 않는다.

```powershell
git apply --check archives/breeding-server-zdo-2026-10-05/reapply.patch
git apply archives/breeding-server-zdo-2026-10-05/reapply.patch
dotnet build FeedLikeGrandma.csproj -c Debug -p:DeployToGame=true
```

이번 보관 작업에서는 `--check`까지만 실행했으며 활성 구현은 로컬 캐시 방식이다. 재적용 후에는 snapshot/tests/README.md의 번식 테스트를 다시 수행해야 한다.

## 보관 구현의 검증과 한계

서버의 주변 ZDO로 경계 밖 미로드 개체까지 집계한다. 요청자 소유권, 개체 종류, 만료·중복 응답과 소유권 revision을 검사한다. 기존 동물 인스턴스의 반경·한도를 보존하며 서버 반치트 강제 정책은 아니다. 이미 진행 중인 임신·출산은 제한하지 않는다.

당시 Debug 빌드 및 로컬 DLL 해시 일치, source-link 논리 검사 178개, 기존 YAML/Orb 검사 37개, 원본 1.0.16 클라이언트·서버 API 검사, 양쪽 원본 Mono에서의 Harmony 재호출 검사에 통과했다. 실제 Unity 월드·2인 데디케이트 서버 실행과 성능 측정은 하지 않았다. 이 결과는 활성 롤백 구현의 테스트 결과가 아니다.

성능 보완은 아직 구현하지 않았다. 예시 반경 10m에서도 9개 zone의 모든 ZDO를 먼저 모으므로 건축물이 많은 곳에서 복사·할당 비용이 크다. 최소 zone 사각형의 순차 조회, 한도 도달 시 다음 zone 수집 중단, 임시 버퍼 재사용과 프레임당 처리량 제한이 후속 검토 사항이다. 64개 동시 코루틴 제한은 프레임 시간 예산이 아니다. 거리 0 이하는 서버 월드 전체를 세며 큰 범위 조회는 원자적인 스냅샷이 아니다.

롤백한 활성 구현은 기존처럼 동물 소유 피어에 로드된 성체·새끼만 세므로, 시뮬레이션 거리 차이 등으로 경계 반대편 개체가 빠지는 한계도 다시 존재한다.
